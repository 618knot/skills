# PRモード（コード変更・ブランチ差分）仕様

PR提出前またはレビュー依頼前のコード差分を対象に、変更意図・境界条件・テスト盲点・システム波及・関連技術知識を確認するためのルール。

---

## 1. 入力ソースの取得

1. **PRが存在する場合（現在のブランチまたはユーザー指定のPR番号/URL）**：
   - `gh pr view <PR番号またはURL省略時は現在ブランチ> --json number,title,url,body,baseRefName,headRefName,files`
   - `gh pr diff <PR番号またはURL省略時は現在ブランチ>`
2. **PR作成前のブランチ／作業ツリーの場合（`gh pr view` が該当なし）**：
   - ベースブランチを特定（例：`origin/main` / `main`）し、`git status`、`git diff <base>...HEAD`（未コミット変更を対象にする場合は `git diff` / `git diff --staged`）、`git log <base>..HEAD --oneline` を取得する。
   - PR番号がないため、ログ記録時の `target_number` は `null`、ファイル名識別子はブランチ名スラッグとする。

---

## 2. ノイズ差分の除外ルール

以下に該当するファイル・差分は出題対象から除外する（ただし依存関係ファイル追加の検知だけはチェックする）：

- **Lockfile**：`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lockb`, `Cargo.lock`, `go.sum`, `Gemfile.lock`, `poetry.lock`, `uv.lock`, `composer.lock`, `Podfile.lock` 等
- **バイナリ・メディア・フォント**：画像、PDF、音声/動画、フォント、コンパイル済みアーカイブ
- **ビルド生成物・自動生成コード**：`dist/`, `build/`, `.next/`, `out/`, `coverage/`, `*.min.*`, `*.bundle.*`, `*.pb.go`, `*.generated.*`, スナップショット巨大差分
- **フォーマット・空白のみの差分**：機能や制御フローに影響しないインデント・改行・クォート統一のみの差分

---

## 3. オンデマンドのコンテキスト補強（diff単体での推測禁止）

diff の断片だけを見て問題を作ったり正誤判定したりしない。変更内容に応じて必要な周辺ファイル（目安1〜4ファイル）を実際に読み込んで裏取りする。

- **呼び出し元・利用箇所**：変更した関数・コンポーネント・APIの呼び出し元と型/インターフェース定義
- **関連テストファイル**：追加・更新されたテスト、または既存テストのスイート
- **スキーマ・設定・プロジェクト規約**：DBマイグレーション、環境変数/設定、関連ADRやリポジトリ内のルール文書（`AGENTS.md`, `docs/` 等）
- **同一セッションバイアスの排除**：この会話内でAI自身が実装した直後の場合は、会話履歴の記憶に頼らず、実際のdiffと周辺ファイルをゼロベースで読み直して批判的に検証する。

---

## 4. 規模・リスク判定とトリアージ

除外後の実質diffを見て規模・リスクを判定し、`question-design.md` の問題数・配分を決める。

| 区分 | 判定基準の例 | 推奨アクション |
| :--- | :--- | :--- |
| **極小・自明** | typo修正、コメント・ドキュメントのみの軽微修正、フォーマット調整、20行未満で条件分岐・副作用・状態変更のない変更 | 「今回は軽微なためスキップ（または2問の簡易チェック）でよいですか？」と確認する |
| **標準** | 通常の機能追加、バグ修正、中規模リファクタリング、エンドポイント/コンポーネント追加 | **4問前後**を出題 |
| **高リスク・複雑** | 以下の高リスク要素を1つ以上含む変更、または複数モジュールに跨る大規模・AI生成比率の高い変更 | **5〜6問**を出題 |

### 高リスク要素（1つでも該当すれば重点出題）
- DBスキーマ変更・マイグレーション・トランザクション・データ整合性
- 認証・認可・権限境界・セッション・暗号・機密情報・課金/決済
- 非同期処理・並行制御・ロック・キュー・キャッシュ無効化・リトライ
- 外部API連携・タイムアウト・フォールバック・Webhook
- 新規依存パッケージの追加
- 既存テストの期待値・アサーションの書き換え

### AI生成コード特有の落とし穴（検知時は最低1問を必ず割り当てる）
diff 内に以下を見つけた場合、必ずその箇所を狙った問いを1問以上組む：
1. **新規依存追加**：標準機能や既存ライブラリで代替できないか、メンテナンス/サイズ/ライセンス上の懸念がないか。
2. **既存ヘルパーとの重複**：リポジトリ内に同等の共通関数があるのに新規実装していないか。
3. **既存テストの期待値書き換え**：バグ修正ではなく、新実装にテストを合わせて仕様変更を隠していないか。
4. **防御・検証の静かな弱体化**：空の `catch`、雑なフォールバック値、認可・バリデーション条件の緩和が入っていないか。

## 5. PRモードの5カテゴリと作問例

5カテゴリから対象の特性に合わせてバランスよく選ぶ（同じ観点ばかり重ねない）。

### カテゴリ1：意図・目的の抽象説明（推奨：記述式 1〜2文）
コードの行単位の逐語訳ではなく、「何のために変え、何が変わってはいけないか（不変条件）」を問う。
- **よい問い**：「この変更によって、呼び出し元から見た振る舞いは何がどう変わり、逆に『絶対に変わってはいけない仕様（不変条件）』は何ですか？実装の1行ずつの説明ではなく目的で答えてください。」
- **悪い問い**：「`src/auth.ts` の42行目で追加された変数名は何ですか？」

### カテゴリ2：設計判断・トレードオフ（推奨：記述式 1〜2文）
なぜ別案ではなくこの設計を選んだか、何を得て何を受け入れたかを問う。
- **よい問い**：「キャッシュの更新を同期処理ではなく非同期イベントにした理由は何ですか？同期にした場合と比べて、どんなリスクや制約を受け入れていますか？」
- **悪い問い**：「この変更はクリーンに設計されていますか？（Yes/No）」

### カテゴリ3：境界条件・反例トレース（推奨：競合選択肢付きMC または 記述式）
異常系・空値/`null`・境界値・並行競合・タイムアウト時の挙動予測や、特定の異常結果を引き起こす入力の逆トレースを問う。
- **よい問い（MC例）**：「外部APIがタイムアウトし、かつ対象レコードが空配列 `[]` を返したとき、この関数の戻り値とDB状態はどれになりますか？\nA. 正常終了し既存データ維持 / B. 空で上書きして保存 / C. 例外送出してロールバック / D. 上限までリトライ後に空配列を返す」
- **悪い問い**：「正常系の入力 `[1, 2, 3]` を渡すと何を返しますか？」

### カテゴリ4：変異・テストの盲点（推奨：競合選択肢付きMC または 記述式）
特定の条件式を書き換える・認可チェックや検証行を消すといった「1点の変異」を入れたとき、既存・追加テストが失敗として検知できるかを問う。
- **よい問い**：「もし今回のdiffの境界判定を `>=` から `>` に変えた（または認可チェックの1行を消した）場合、現在の自動テストは失敗しますか？失敗するとしたらどのテストケースですか？」
- **悪い問い**：「単体テストはすべてパスしていますか？」

### カテゴリ5：システム波及・運用リカバリ（推奨：記述式 1〜2文）
呼び出し元・他モジュール・下流ジョブへの波及や、本番リリース後に想定外の不整合・劣化が起きた際の検知方法と安全な切り戻し手順を問う。
- **よい問い**：「この変更を本番リリースした後に想定外のレイテンシ劣化やデータ不整合が起きた場合、どのログ／メトリクスで検知し、既存データを含めて安全に切り戻す手順はどうなりますか？」
- **悪い問い**：「関連ファイルに影響はありませんか？」

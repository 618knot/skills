# 共通作問ルール・配分・禁止事項・内部難易度

両モード共通で適用する、問題数・配分・出題形式・禁止ルール・内部難易度の設計基準。

---

## 1. 問題数と配分（対象固有の要点 vs 関連する技術知識）

- **総問題数**：目安 **4問**（最小 **2問** 〜 最大 **6問**）。所要時間 1〜3 分で完結する負荷に収める。
- **配分対象**：すべての問題は次のどちらかに分類する（ログ記録時にも明記する）。
  - **対象固有の要点**：変更意図、調査結論、設計判断、境界条件、テスト盲点、影響範囲、前提条件など、今回の対象そのものの理解。
  - **関連する技術知識**：今回の対象で使われるフレームワーク・言語・DB・ネットワーク・認証・並行処理・アーキテクチャ等の仕様や概念。

### 規模・リスク別 配分ガイド

| 規模・リスク区分 | 総問題数 | 対象固有の要点 | 関連する技術知識 | 備考 |
| :--- | :--- | :--- | :--- | :--- |
| **極小・自明** | 0問（スキップ提案）または 2問 | 2問 | 0問 | 新規API・微妙な仕様に触れる場合のみ `1 + 1` 可 |
| **小規模・単純** | 2〜3問 | 2問 | 0〜1問 | 新機能や仕様依存があれば技術知識を1問入れる |
| **標準** | **4問**（基本） | 2〜3問 | 1〜2問 | 最も標準的なバランス |
| **高リスク・重要選定** | **5〜6問** | 3〜4問 | 2問 | 未知技術・新DB/FW導入など技術比重が高い場合は `3 + 3` も可 |

### 関連する技術知識の作問原則
- **対象の文脈に必ず結びつける**：一般論の単語クイズにはしない。「今回のコード／技術選定でその仕様・概念がどう効くか」を問う。
  - 例（良）：「今回導入したトランザクション内で `READ COMMITTED` のまま『存在確認 → INSERT』を行うと、並行リクエスト時に何が起き得ますか？」
  - 例（悪）：「トランザクション分離レベルを4つすべて挙げてください。」

## 2. 出題形式の選定基準

1. **記述式（短答式：1〜2文）を基本とする**（全体の過半数）：
   - 意図・結論・トレードオフ・運用リスク・根拠の妥当性など、自分の言葉で構造化して言語化させる問いに使う。
   - 回答の目安を添える（例：「1〜2文で自分の言葉で答えてください」）。
2. **競合選択肢付き選択式（3〜4択MC）を一部（目安1〜2問）組み合わせる**：
   - 境界条件の挙動予測、変異（1行改変・削除）時のテスト検知有無、前提の切り分けに適する。
   - **選択肢設計ルール（競合選択肢）**：
     - 明らかなダミーや不自然な冗談選択肢を混ぜない。
     - 実務で開発者が陥りやすい現実的な誤解（`null` と空配列の混同、トランザクションのロールバック漏れ、デフォルト設定の誤認、非同期の競合など）で選択肢を作る。
     - 選択後に「一言で理由もあれば添えてください」と促してもよい（必須にはせず負担を抑える）。
3. **ネタバレ・再認クイズの回避**：
   - 問題文や引用スニペットの中に答えのキーワードがそのまま並んでいる状態を作らない。
   - 挙動予測や変異検証の問いでは、答えに直結する実装行や結論の記述を問題文中で伏せる（または最小限のインターフェース・条件だけを提示する）。

## 3. 禁止問題リスト（厳守）

以下のパターンの問題は**一切作成してはならない**：

- 構文・変数名・関数名・ファイルパス・行番号の暗記クイズ
- ドキュメントや diff 内の表現の穴埋め・単なる単語の復唱
- `Yes / No` や「確認しましたか？」で終わる受動的チェックリスト形式
- 正常系（ハッピーパス）のみの単純なトレース
- 今回のPR・Issueの文脈と切り離された汎用トリビア問題
- 出題中・回答待ち中に、内部難易度（`Lv.1`〜`Lv.3`）や採点基準をユーザーに見せること

---

## 4. 内部難易度の基準（ログ記録専用・出題時は非公開）

出題計画時に各問題へ `Lv.1`〜`Lv.3` を割り当て、**出題中には表示せず、終了時の Obsidian ログにのみ記録する**。

| 内部難易度 | 定義 | 対応する問いの例 |
| :--- | :--- | :--- |
| **Lv.1** | 局所的な挙動・基本仕様・調査事実の確認 | 単一関数・設定変更の直接的な役割、文書内の主要結論・採用要件の確認、関連APIの基本仕様 |
| **Lv.2** | 境界条件・エッジケース・変異検証・根拠の妥当性・関連技術の応用 | `null`/空値/タイムアウト時の挙動、条件式1点改変時のテスト検知有無、一次情報と推測の切り分け、技術仕様の具体的適用 |
| **Lv.3** | 設計トレードオフ・システム全体の波及（マクロ構造）・反証条件・運用/実装リスク | 別案との比較と受け入れたリスク、他サービス/呼び出し元への波及と切り戻し、結論が覆る条件、本番障害・移行時のボトルネック |

### 難易度バランス目安
- すべて `Lv.1` のみで終えない。
- 標準（4問）なら、`Lv.1` 1問 + `Lv.2` 1〜2問 + `Lv.3` 1〜2問 のように中〜高抽象度の問いを必ず含める。
- 5〜6問の高リスク・重要選定では、`Lv.2` と `Lv.3` を中心に構成する。

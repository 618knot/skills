# 調査Issue / ドキュメントモード仕様

コード差分を伴わない調査Issue・RFC・技術選定ドキュメント・原因調査レポート・設計メモを共有・提出する前に、結論の妥当性・根拠の強さ・盲点・運用リスク・関連技術知識を確認するためのルール。

---

## 1. 入力ソースの取得

1. **GitHub Issue の場合**：
   - `gh issue view <Issue番号またはURL> --json number,title,url,body,comments,labels`
   - 関連PRやリンク先Issueがあればタイトル・概要レベルで参照関係を確認する。
2. **ローカルの Markdown / ドキュメントファイルの場合**：
   - 指定されたファイルを `read_file` で読み込む（長大な場合は見出し構造を把握したうえで必要範囲を読む）。
3. **チャット上の調査メモ・下書きの場合**：
   - 提示されたテキスト全体を対象とし、関連リポジトリがワークスペースにある場合はそこも参照対象とする。

---

## 2. オンデマンドの裏取り参照（推測禁止）

ドキュメント内に書かれた記述を鵜呑みにせず、リポジトリ内から検証できる事項はオンデマンドで読み込んで突き合わせる。

- **参照コード・設定の確認**：ドキュメントが言及している現行コード、設定ファイル、DBスキーマ、`package.json` / `go.mod` / `pyproject.toml` 等を実際に確認し、現状認識のズレがないかを見る。
- **既存ドキュメントとの整合性**：関連する既存のADR・設計書・規約があれば1〜2件確認し、前提や方針と矛盾していないかを見る。
- **事実と推測の分離チェック**：一次情報（実測値・公式仕様・ソースコード上の確認結果）に基づく主張と、推測・未検証・伝聞が混ざっている箇所を特定し、カテゴリ2・4の出題材料にする。

---

## 3. 規模・重要度判定とトリアージ

対象の性質・意思決定の重さに応じて、`question-design.md` の問題数・配分を決める。

| 区分 | 判定基準の例 | 推奨アクション |
| :--- | :--- | :--- |
| **極小・短いメモ** | 単なる作業メモ・議事録・事実の転記のみで、意思決定や設計判断を伴わない | 「今回は意思決定を伴わないメモのためスキップ（または2問の簡易チェック）でよいですか？」と確認する |
| **標準** | 通常の調査Issue、バグ原因調査レポート、単一仕様の確認まとめ、小規模な実装方針メモ | **4問前後**を出題 |
| **重要・高インパクト** | 技術選定（ライブラリ/FW/DB/SaaS/インフラ採用）、アーキテクチャ方針決定、データ移行・破壊的変更、不可逆またはコストの高い判断、複数案比較 | **5〜6問**を出題 |

---

## 4. 調査Issue / ドキュメントモードの5カテゴリと作問例

5カテゴリから対象の性質に合わせてバランスよく選ぶ。

### カテゴリ1：結論の抽象要約（推奨：記述式 1〜2文）
ドキュメントの細部や見出しをなぞるのではなく、「調査の結論は一言で何か」「読み手・意思決定者に何を決めてほしいか」を問う。
- **よい問い**：「この調査ドキュメントを読んだ意思決定者に、最終的に『何を判断・承認してほしい』のかを1〜2文で言うと何になりますか？（背景説明ではなく決めるべきこと自体で答えてください）」
- **悪い問い**：「ドキュメントの2章に記載されている推奨ライブラリの名前は何ですか？」

### カテゴリ2：根拠の検証（推奨：記述式 または 競合選択肢付きMC）
結論を支える一次情報・検証結果・実測値は何か、逆に「検証した事実」と「推測・前提」が混ざっていないかを問う。
- **よい問い**：「案Aが『性能面で有利』とする結論は、実測ベンチマーク（一次情報）に基づくものですか、それとも仕様・記事からの推測ですか？既存コードベースで実測せずに残っている不確実性はどこですか？」
- **悪い問い**：「結論の根拠はドキュメントに書かれていますか？（Yes/No）」

### カテゴリ3：比較・トレードオフ（推奨：記述式 1〜2文）
不採用にした代替案が明確に優れている点（捨てたメリット）は何か、また「どの条件が変われば結論が覆るか（反証条件）」を問う。
- **よい問い**：「今回見送った案Bが採用案より明確に優れている点は何ですか？また、今後どの前提条件（データ量・チーム要件・コスト等）が変わったら案Bへ再検討すべきですか？」
- **悪い問い**：「案Aのメリットをドキュメントから3つ挙げてください。」

### カテゴリ4：盲点・前提の問い直し（推奨：競合選択肢付きMC または 記述式）
今回の調査スコープから漏れている領域・未検証の境界、あるいは暗黙に置いている前提条件（運用負荷、障壁、既存制約との相性など）を問う。
- **よい問い（MC例）**：「今回の調査対象から意図的または暗黙に外れている範囲のうち、本番運用時に最も想定外の制約になり得るのはどれですか？\nA. ローカル検証環境と本番のデータ件数差 / B. 既存認証ミドルウェアとのセッション互換 / C. 障害発生時のロールバック可否 / D. この中に該当なし（すべて実測済み）」
- **悪い問い**：「調査漏れの点はありませんか？」

### カテゴリ5：次のアクション・リスク（推奨：記述式 1〜2文）
この調査結果をもとに実装・PoC・移行へ進む際、最も詰まりそうな技術的ボトルネックや、着工前に先手を打つべきリスクを問う。
- **よい問い**：「この方針で実装・移行を進める場合、最初の実装タスクで最も想定外の工数や手戻りが発生しそうな箇所はどこで、着手前に何を検証・合意しておくべきですか？」
- **悪い問い**：「次のアクションはIssueの末尾に書いてある通りでよいですか？」

# 【Layer 2】PR特化ビジュアル設計規約・PRタイプ別演出＆アンチパターン集

本ドキュメントは、PR 解説アニメーションにおいて「生 diff 丸映しによる視認性崩壊」と「認知過負荷」を防ぎ、コード変更の因果を直感的に伝えるためのビジュアル設計ルールと 8大アンチパターン（Gotchas）を定義する。

---

## 1. PR解説の基本画面レイアウト（2ペイン同期シアター）

PR 解説アニメーションでは、単一キャンバスではなく **「抽象（実行フロー）」と「具体（核心コード）」を並置同期する 2ペイン構造** を標準とする（Bret Victor の複数表現連動・Chandler & Sweller の注意分割排除）。

```text
+-----------------------------------------------------------------------+
| [PRタイトル / 変更規模バッジ]        [Act 1〜5 プログレスバー]          |
+------------------------------------+----------------------------------+
| 左ペイン（55〜60%幅）               | 右ペイン（40〜45%幅）             |
| 抽象アーキテクチャ / 実行フローSVG   | 核心コード抜粋（最大 8〜12行）     |
| ・変更前シルエット残像（Trace）      | ・file/path.ts:L42-L53 バッジ     |
| ・Progressive Path による因果伝播   | ・Before / After 切替・強調行     |
| ・非注目ノードのディミング(0.2)      | ・非注目行のディミング(0.3)        |
+------------------------------------+----------------------------------+
| 下部固定キャプション（最大2行・日本語 <= 32文字・Phase A 読解静止保証）  |
| [再生/一時停止] [◀ 1ビート戻す] [再再生] [1ビート進む ▶] [速度] [軽減]  |
+-----------------------------------------------------------------------+
```

### 1.1 コード抜粋の厳格ルール（Max 12 Lines & Semantic Focus）
- **行数上限**: 1ビートで右ペインに表示するコードは **最小3行〜最大12行** に厳格制限する（理想 6〜10行）。
- **コンテキスト行のディミング**: 変更・注目すべき 1〜4行だけを 100% 不透明度＋左端カラーバー（追加＝エメラルド、削除＝ローズ、リスク注意＝アンバー、変更焦点＝スカイ）で強調し、周囲の文脈行は `opacity: 0.35` へ後退させる。
- **Magic Move 風の Before → After 表現**: 削除行と追加行を延々と縦積みするのではなく、Phase C のモーション同期に合わせて「削除行が薄く取り消し線化（または残像化）→ 追加行が強調スライド/ハイライト出現」することで、何から何へ置き換わったかを1画面内で直感化する。
- **`file:line` バッジ必須**: 右ペイン上部に必ず実ファイルのパスと行範囲（例：`src/auth/guard.ts:L88-L96`）を表示し、視聴後にエディタで即座に確認できるようにする。
- **双方向 `data-key` 連動**: 左ペインのフロー矢印・ノードと、右ペインの対応コード行に同じ `data-key` を付与し、ビート進行時の自動強調だけでなくマウスホバーでも双方向に連動ハイライトさせる。

## 2. PRタイプ別ビジュアル演出テンプレート

| PRタイプ | 第2幕（Before）の見せ方 | 第3幕（Core Flow）の主演出 | 第4幕（Risk Audit）の焦点 |
| :--- | :--- | :--- | :--- |
| **`bugfix`** | 異常入力からバグ発火点までの**赤色 Progressive Path** と壊れた状態 | 原因箇所のコードズーム → 修正行の置換 → **緑色パス**が正常終端へ到達（旧赤パスを薄い残像で残す） | 同種のエッジケース（null/空/リトライ/競合）が他経路に残っていないかの確認 |
| **`feature`** | 既存リクエスト/データフロー（低彩度）と「今回差し込む拡張ポイント」 | 新規ノード・新分岐を `Draw-on` で追加し、データトークンが新経路を通る様子を `Follow-Path` で示す | 既存パス（不変条件）への副作用・新規権限チェック・パフォーマンス/DB負荷 |
| **`refactor`** | 外部I/F（入力→出力の境界枠）を固定したまま、内部の絡まった依存線を提示 | 外部I/Fの境界枠を一切動かさず（180°ルール厳守）、内部ノードを整理・統合へ `Staged Morph` | 振る舞いが微妙に変わり得る箇所（例外型・順序・既存テスト書き換え有無） |
| **`architecture`** | 旧コンポーネント間シーケンス／データストア構成の俯瞰図 | `enter` / `update` / `exit` 対応表に基づき、キュー・キャッシュ・新テーブルの追加とデータ流路変更を段階構築 | マイグレーション互換性、キャッシュ整合性、部分失敗時のロールバック手順 |
| **`ui`** | 変更前のワイヤーフレーム／状態遷移図と課題（例：二重送信・レイアウト崩れ） | ユーザーイベント発火 → 状態遷移 → 変更後レイアウト・ガード状態の Before/After 比較 | ローディング中・エラー時・狭い画面・キーボード操作時のエッジ状態 |

## 3. PR解説アニメ特有の8大アンチパターン（Gotchas #1–#8）と MUST / NEVER 制約

`explanatory-animation` の基本モーション規約（無音5フェーズ同期・MOT上限4個・Slow-in/out・定着ホールド `>= 1000ms`・決定論的 `render(state)`・`prefers-reduced-motion`）に加え、PR解説特有の以下の8つの失敗を遮断する。

### Gotcha #1: 生 diff の丸映し（Wall of Diff）
- **症状**: `git diff` の数十行〜数百行をそのまま画面に並べてスクロール・フェードする。
- **敗因**: 文字が小さすぎて読めず、変更の因果構造（データフロー）が完全に埋もれる。
- **MUST / NEVER**:
  - **NEVER**: 1ビートに 13行以上のコードや生の unified diff 塊を詰め込まない。
  - **MUST**: 核心となる 6〜10行（最大 12行）だけを抜粋し、必ず左ペインの抽象フロー図と並置する。

### Gotcha #2: Git ファイル名アルファベット順の羅列（Alphabetical File Tour）
- **症状**: `a.ts` → `b.ts` → `c.ts` のように、GitHub の Files Changed の並び順そのままにビートを並べる。
- **敗因**: 呼び出し関係や因果順序がバラバラになり、頭の中で実行順序を組み立て直す巨大な認知負荷がかかる（Baum et al., 2019）。
- **MUST / NEVER**:
  - **NEVER**: ファイルパス順でシーンを構成しない。
  - **MUST**: 実行経路・依存順（Entry Point → コアロジック → データ/副作用 → テスト）へ意味的クラスタリングして並べる。

### Gotcha #3: 結論の後出し・焦らし構成（Misplaced Suspense）
- **症状**: 3Blue1Brown の数理動画のように、最初2〜3ビートまで「何のPRか・結局何が変わるのか」を言わずに細部から入る。
- **敗因**: PR 理解では全体地図（メンタルフレーム）が先にないと各変更行の意図を位置づけられない（Bacchelli & Bird, 2013）。
- **MUST / NEVER**:
  - **NEVER**: 第1幕に結論（Why / What / 影響範囲）がない導入を作らない。
  - **MUST**: 第1幕（TL;DR & Blast Radius）で最初に全体像と不変条件を明示する。

### Gotcha #4: diff 単体からの当て推量・存在しない行番号の捏造（Ungrounded Hallucination）
- **症状**: diff に映っていない呼び出し元や型の挙動を推測で図解し、コード抜粋に曖昧・不正確な行番号や省略改変コードを書く。
- **敗因**: 自分用ツールとして最も致命的な「誤ったメンタルモデルの刷り込み」と、コードへ飛び直したときの不信感を生む。
- **MUST / NEVER**:
  - **NEVER**: 周辺ファイルを読まずに呼び出し元の挙動を断定したり、存在しない行番号・改変した擬似コードを実ファイルパス付きで表示しない。
  - **MUST**: 変更に関連する周辺 1〜4ファイルを実読し、コード抜粋には実コードと正確な `file:line` を対応づける（省略行がある場合は `// ...` と明記する）。

### Gotcha #5: 正常系ハッピーパスだけの美談化（Missing Risk & Edge Cases）
- **症状**: PRがやりたい正常系の流れだけ綺麗に動かして終わり、エラー系・境界値・DB影響・AI生成コードの怪しい変更に触れない。
- **敗因**: 特に AI 実装 PR を自分で確認する際、正常系は一見正しいため、隠れた副作用・空 `catch`・テスト期待値の書き換えを見逃す原因になる。
- **MUST / NEVER**:
  - **NEVER**: 正常系フローだけで解説を完結させない。
  - **MUST**: 第4幕（Edge Cases & Risk Audit）で最低1ビートを異常系・境界条件・高リスク箇所・不変条件チェックに割り当てる。

### Gotcha #6: 字幕切替とコード/図解モーションの同時発火（Visual Channel Overload）
- **症状**: 下部の説明文が切り替わった瞬間に左のフロー図と右のコード行ハイライトが一斉に動く。
- **敗因**: 無音Web画面では「キャプションを読む」「コードを読む」「図の動きを追う」の3つが同一視覚チャネルで衝突する（Berney & Bétrancourt, 2016）。
- **MUST / NEVER**:
  - **NEVER**: Phase A（読解静止）完了前に主モーションやコード切替を開始しない。
  - **MUST**: キャプションを最大2行（日本語 $\le 32$ 文字）に抑え、日本語 `4.0 CPS`（英語 `17 CPS`）算出の読解静止時間＋`200–400 ms` のディミング誘導の後に主動作を開始し、完了後に `>= 1000 ms`（重要ビート `>= 1800 ms`）の定着ホールドを置く。

### Gotcha #7: Before/After での空間配置反転と残像の欠如（Spatial Disorientation & Transience）
- **症状**: Before では左にあった呼び出し元が After では上へ移動したり、変更前の経路が完全に消えてどこが変わったか分からなくなる。
- **敗因**: 180°ルール違反による空間迷子（Smith, 2012）と、一過性情報効果（Sweller, 2011; IEEE TVCG 2025 の履歴保持 `1.49倍` 効果）。
- **MUST / NEVER**:
  - **NEVER**: Before と After で既存ノードの座標配置を理由なく動かしたり、変更前経路を跡形もなく消さない。
  - **MUST**: 既存ノードの座標を固定し、変更前経路を薄い残像（`opacity: 0.18`, 破線）として残した上に変更後経路を重ねる。

### Gotcha #8: 巻き戻し不可の一本道再生と過剰モーション（Irreversible Playback & Motion Bloat）
- **症状**: `setTimeout` の連鎖で再生され、「第3幕のコード変更だけ見返したい」「一時停止してコードをじっくり読みたい」ができない。
- **敗因**: コード解説では視聴者が気になる箇所で必ず一時停止・1ビート戻し・手動ステップ送りを行う（Hundhausen et al., 2002; WCAG 2.2 SC 2.3.3）。
- **MUST / NEVER**:
  - **NEVER**: `setTimeout` 連鎖や不可逆な CSS `@keyframes` 一発再生を使わない。背景パーティクルや誇張バウンスも禁止する。
  - **MUST**: 単一状態 `tMs` の純粋関数 `render(state)` で駆動し、一時停止・1ビート戻し/送り・再再生・幕ジャンプ・速度変更（`0.5x–2.0x`）・手動ステップモード・`prefers-reduced-motion` 自動検知＋手動トグルを標準装備する。
